BRTGC Engineering Assessment  
Project Title  
HRFlow — HR & Internal Communication Management Platform  
 
Objective  
Build a modern, secure, and scalable HR and Internal Communication Management Platform  for an 
organization.  
HRFlow should provide organizations with a centralized platform to:  
• Manage employees  
• Manage hierarchical departments  
• Track employee attendance  
• Manage employee leave requests  
• Send internal communications  
• Share files and documents through messages  
• Monitor important HR and organizational activities  
The purpose of this assessment is to evaluate your ability to design and implement a real -world 
business application while demonstrating:  
• Engineering thinking  
• Software architecture  
• Database modelling  
• Problem -solving ability  
• Product thinking  
• UI/UX implementation  
• Code maintainability  
• Type safety  
• Security awareness  
• Ability to build scalable business systems  
You may use AI tools during development. However, you are expected to fully understand the 
implementation , including the architecture, database design, business rules, and technical decisions 
made during development.

Core Features  
1. Authentication & Authorization  
Implement a secure authentication and authorization system.  
Authentication  
Users should be able to:  
• Register  
• Log in  
• Log out  
• Maintain a persistent session  
• Access protected application areas  
The implementation should include:  
• Secure password hashing  
--- PAGE 3 ---
• Input validation  
• Authentication error handling  
• Session persistence  
• Protected routes  
• Secure session management  
User Roles  
The system should support at least the following roles:  
• Admin  
• HR Manager  
• Employee  
Roles should determine what actions and resources a user can access.  
Examples:  
• Admin can manage the organization and its users.  
• HR Managers can manage employees, departments, attendance and leave workflows 
according to their permissions.  
• Employees can access their own information, attendance, leave requests and authorized 
communications.  
Authorization should be enforced server -side, not only through UI visibility.  
 
2. Employee Management  
The system should provide employee management functionality.  
Each employee should contain, at minimum:  
• Full name  
• Email address  
• Phone number  
• Department  
• Position  
• Employment status  
• Date joined  
• Profile image — optional  
Employee Operations  
Authorized users should be able to:  
--- PAGE 4 ---
• Create employees  
• Edit employee information  
• View employee profiles  
• Search employees  
• Filter employees  
• View employees by department  
• Deactivate employees  
Employee deactivation should preferably preserve historical records such as:  
• Attendance  
• Leave requests  
• Messages  
• Activities  
Deleting an employee should therefore not unnecessarily destroy historical business records.  
 
3. Department Management  
Departments should be modeled as a hierarchical organizational structure , rather than as a flat list.  
Each department should contain:  
• Department name  
• Description  
• Department head  
• Parent department — optional  
• Child departments  
Example Department Structure  
Organization  
│ 
├── Human Resources  
│   ├── Recruitment  
│   ├── Training & Development  
│   └── Employee Welfare  
│ 
├── Operations  
--- PAGE 5 ---
│   ├── Field Operations  
│   └── Maintenance  
│ 
└── Finance  
    ├── Accounts  
    └── Audit  
A department can therefore have:  
• A parent department  
• Multiple child departments  
• A department head  
• Multiple employees  
Department Operations  
Authorized users should be able to:  
• Create departments  
• Edit departments  
• View department details  
• Assign department heads  
• Assign employees to departments  
• Move departments within the hierarchy  
• View child departments  
• Navigate to parent departments  
• View employees within a department  
The system should maintain both forward and backward relationships  within the department 
hierarchy.  
For example:  
Recruitment  
     ↓ 
Human Resources  
     ↓ 
Organization  
Recruitment should be able to identify its parent departments, while Human Resources should be 
able to identify its child departments.  
--- PAGE 6 ---
Hierarchy Validation  
The implementation should prevent invalid organizational structures.  
Examples:  
• A department cannot be its own parent.  
• A department cannot become a descendant of itself.  
• Circular department relationships must be prevented.  
• A department head should be an active employee.  
• Appropriate authorization should be required to modify the organizational hierarchy.  
 
4. Attendance Management  
Employees should be able to manage their daily attendance.  
Employee Actions  
Employees should be able to:  
• Clock in  
• Clock out  
• View their attendance history  
• View their attendance for a selected period  
Attendance Requirements  
The system should maintain daily attendance records.  
The implementation should:  
• Prevent duplicate clock -ins for the same attendance period  
• Prevent invalid clock -out operations  
• Validate attendance state transitions  
• Record timestamps  
• Preserve attendance history  
Attendance Statistics  
The dashboard should be able to display statistics such as:  
• Employees present today  
• Employees absent  
• Employees who have not clocked out  
• Attendance history  
--- PAGE 7 ---
• Attendance trends  
 
5. Leave Request System  
Employees should be able to submit leave requests through the platform.  
Leave Request Fields  
Each leave request should contain:  
• Leave type  
• Start date  
• End date  
• Reason  
• Status  
• Requester  
• Submission date  
• Review information where applicable  
Employee Actions  
Employees should be able to:  
• Submit leave requests  
• View their leave requests  
• View leave status  
• Review previous leave requests  
HR/Admin Actions  
Authorized HR Managers and Admins should be able to:  
• View pending leave requests  
• Approve leave requests  
• Reject leave requests  
• Review leave history  
Leave Status  
At minimum, support:  
PENDING  
APPROVED  
REJECTED  
--- PAGE 8 ---
The system should validate:  
• Start date  
• End date  
• Date ordering  
• Invalid or overlapping requests where applicable  
• Unauthorized approval/rejection  
• Invalid status transitions  
The leave workflow should preserve an appropriate audit trail of important actions.  
 
6. Internal Messaging & Organizational Communication  
HRFlow should provide an internal communication system that supports communication between 
employees and departments.  
The messaging system should support:  
1. Employee -to-Employee messaging  
2. Employee -to-Department messaging  
3. Department -to-Department messaging  
4. Department -to-Employee messaging  
The system should use a reusable conversation/message architecture rather than implementing each 
communication type as a completely separate system.  
 
6.1 Employee -to-Employee Messaging  
Employees should be able to:  
• Send private messages to another employee  
• View conversation history  
• Reply to messages  
• View message timestamps  
• View sender information  
• Attach files to messages  
Privacy  
Employee -to-employee conversations are considered individual/private communications . 
Department hierarchy should not automatically grant department heads access to private 
employee conversations . 
--- PAGE 9 ---
For example:  
HR 
│ 
└── Recruitment  
    │ 
    ├── Alice  
    └── Bob  
If Alice sends a private message to Bob:  
Alice ───────────> Bob  
The HR Head should not automatically gain access to the conversation simply because Alice and Bob 
belong to departments below HR.  
 
6.2 Employee -to-Department Messaging  
Employees should be able to send communications to an entire department.  
Example:  
Employee  
    │ 
    └────────> HR Department  
A message may contain:  
• Text 
• Attachments  
• Timestamp  
• Sender information  
• Department recipient  
Department members and authorized department users should be able to access the communication 
according to the organization's communication permissions.  
 
6.3 Department -to-Department Messaging  
Departments should be able to communicate with other departments.  
Example:  
Human Resources  
       │ 
--- PAGE 10 ---
       └────────> Operations  
Examples of departmental communications may include:  
• Requests  
• Announcements  
• Reports  
• Operational updates  
• Administrative communications  
• Document sharing  
The system should maintain a complete conversation history.  
 
6.4 Department -to-Employee Messaging  
Authorized department users should be able to send messages to individual employees.  
Example:  
HR Department  
      │ 
      └────────> Employee  
This can be used for:  
• HR notifications  
• Requests  
• Administrative communication  
• Employee -specific instructions  
• Document sharing  
 
6.5 Department Hierarchy & Message Visibility  
Departmental communication should take the organization's department hierarchy into account.  
For example:  
Organization  
│ 
├── Human Resources  
│   └── Recruitment  
│ 
--- PAGE 11 ---
└── Operations  
If the Recruitment Department  sends a departmental communication, the communication may be 
visible to authorized department heads within its organizational hierarchy.  
The hierarchy can therefore be resolved upward:  
Recruitment  
     ↑ 
Human Resources  
     ↑ 
Organization  
This means an appropriate departmental communication originating from Recruitment can be 
accessible to:  
• Recruitment Head  
• Human Resources Head  
• Higher -level authorized department heads  
subject to the application's authorization rules.  
However, this visibility rule applies to departmental communications only . 
Individual Communication Remains Private  
The hierarchy must not automatically expose private employee -to-employee conversations.  
Therefore:  
Employee ↔ Employee  
is private unless the application's explicit authorization model provides otherwise.  
While:  
Department ↔ Department  
Employee → Department  
Department → Employee  
can participate in organizational communication visibility.  
The implementation should clearly distinguish between individual communication  and 
departmental communication .

Realtime messaging is optional but highly valued .

7. File Sharing Through Messaging  
File sharing should be implemented as an integrated capability of the messaging system . 
Users should be able to attach files directly to messages.  
Example  
--- PAGE 13 ---
Message  
│ 
├── Text 
│ 
├── PDF attachment  
│ 
└── Image attachment  
Supported file examples include:  
• PDF files  
• Images  
• Word/document files  
• Other appropriate business documents  
Expected Functionality  
Users should be able to:  
• Upload a file while composing a message  
• Attach files to messages  
• View attachment information  
• Preview supported files where possible  
• Download attachments  
• Access attachments through the relevant conversation  
File Metadata  
The database should store metadata such as:  
• Original file name  
• MIME type  
• File size  
• Storage reference/key  
• Upload timestamp  
• Message relationship  
The actual file content should preferably be stored using appropriate file/object storage rather than 
directly inside MongoDB.  
The database should contain the metadata and secure reference required to access the file.  
--- PAGE 14 ---
Security  
File uploads should include appropriate:  
• File type validation  
• File size validation  
• Access control  
• Secure file references  
• Authorization checks  
A user should not be able to access an attachment merely by guessing its URL.  
Optional Enhancements  
Candidates may implement:  
• PDF previews  
• Image previews  
• Document previews where supported  
• Drag -and-drop uploads  
• Upload progress  
• Multiple attachments  
• Attachment thumbnails  
 
8. Dashboard  
Create a responsive dashboard providing an overview of the organization's current state.  
The dashboard should display information such as:  
• Total employees  
• Employees present today  
• Pending leave requests  
• Total departments  
• Recent activities  
• Recent messages  
Dashboard information should respect the user's role and permissions.  
For example, an employee should not necessarily receive the same organization -wide statistics 
available to an Admin or HR Manager.  
Dashboard UX

The dashboard should provide:  
• Responsive layout  
• Mobile -friendly interface  
• Clear information hierarchy  
• Loading states  
• Empty states  
• Error states  
• Appropriate visual feedback  
• Easy navigation to frequently used features
